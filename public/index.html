ENGINEERING ARCHITECTURE

Three Paths to HarmonyOS

Porting mature global codebases to HarmonyOS NEXT requires choosing the right architectural seam. Here are the three proven patterns developed by our team.

Pattern 01 · Most Accessible

Flutter Backport Shim

When an upstream Flutter app relies on Google Mobile Services (GMS) plugins unavailable on OHOS, implement the platform interface using a hybrid ArkWeb bridge while keeping the Dart API intact.

Validated In: OpenGMaps
Stock Plugin API
↓
Custom OHOS Platform Interface
↓
ArkWeb JS Bridge + Location Kit
Pattern 02

Native ArkTS Shell + NAPI

For complex C/C++ GUI software like GNU Emacs, wrap the core in an ArkUI Stage-model HAP. Mount an XComponent EGL surface for hardware rendering and connect input events through a thread-safe NAPI bridge.

ArkUI Stage-Model HAP
↓
XComponent Surface (EGL / OpenGL)
↓
NAPI C Bridge ⇄ Upstream C Engine
Validated In: OHEmacs
Pattern 03

Companion Server Bridge

When a complex closed-network protocol lacks official HarmonyOS SDKs, isolate the cryptographic protocol state on an always-on Go daemon and build a slim, responsive ArkTS client connecting via WebSocket push.

Lightweight ArkUI Mobile Client
↕ (WebSocket / REST)
Go Companion Server (whatsmeow)
↕
WhatsApp Multi-Device Protocol
Validated In: WhatIsIt

API Endpoints

Method & Route Description
GET /api/apps Fetch all dossiers. Supports ?q= and ?stack= query params.
GET /api/apps/:id Fetch a single port dossier by unique identifier.
GET /api/contributors List all maintainers and porting credits.
GET /health Production uptime probe. Returns { ok: true }.

Want to add a new port?

Add an entry to data/apps.json, append your contributor profile to data/contributors.json, and submit a pull request!
