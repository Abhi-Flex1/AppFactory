Three Paths to HarmonyOS NEXT

Porting mature global codebases to HarmonyOS NEXT and OpenHarmony 5.0.1 requires choosing the right architectural seam. Depending on upstream constraints, dependency trees, and native bindings, our team has validated three distinct porting patterns.

Pattern 01

The Flutter Backport Shim

Preserving Dart Application Code by Shimming Missing GMS Platform Interfaces via ArkWeb

When a mature Flutter app relies on proprietary Google Mobile Services (GMS) plugins such as google_maps_flutter, directly compiling for OpenHarmony fails because no GMS binary exists on the system.

Instead of rewriting the entire UI in ArkTS, this pattern implements a custom google_maps_flutter_ohos plugin implementing the stock Dart platform interface. It binds to an ArkWeb instance executing Google Maps JavaScript API v3.56 with bidirectional JSON method channels, while dispatching GPS location queries to native OHOS Location Kit.

Key Architectural Benefits

  • 100% Upstream Dart Code Reusability: Screens, state management, models, and business logic remain untouched.
  • No GMS Requirement: Bypasses Google Play Services completely while using official vector tiles.
  • Native Hardware Performance: Hardware-accelerated WebGL tile rendering inside the system ArkWeb engine.

Pattern 02

Native ArkTS Shell + NAPI C Bridge

Embedding Legacy C/C++ GUI & Engine Code in an ArkUI Stage-Model HAP

Decades-old C/C++ GUI systems like GNU Emacs cannot be re-engineered from scratch. Instead, we wrap the engine in a Stage-model ArkTS shell.

The ArkUI front-end mounts an XComponent backed by OpenGL ES / EGL for hardware-accelerated rendering. A lightweight, thread-safe NAPI bridge (libentry.so) bridges the HarmonyOS event loop, forwarding touch inputs, keyboard buffer events, and window metrics directly to the upstream C engine.

Key Architectural Benefits

  • Native GPU Pipeline: Direct EGL rendering with zero canvas copying overhead.
  • Full Lisp Execution: Complete GNU Emacs Lisp VM running on-device via two-stage pdump cross-compilation.
  • Dual-Mode Capability: Supports both Stage-Model GUI application and standalone native terminal CLI binary.

Pattern 03

Companion Server Bridge

Decoupling Closed-Network Cryptography via an Always-On Go Microservice

When a complex communication service lacks public REST APIs or HarmonyOS client SDKs, building a fully compliant native client from scratch carries severe protocol drift and account ban risks.

This pattern isolates the persistent cryptographic session and protocol state machine inside an always-on Go daemon (using whatsmeow). The phone or tablet runs a lightweight, battery-efficient ArkUI client that syncs chats and media over local WebSocket push notifications.

Key Architectural Benefits

  • Session Longevity: Multi-Device session survives mobile process kills, reboots, and sleep cycles.
  • Zero Reverse Engineering in ArkTS: Complex Noise protocol handshakes and protobuf parsing remain in well-audited Go libraries.
  • Native ArkUI Feel: The mobile user interface is 100% native ArkTS, delivering smooth 120Hz scrolling.
